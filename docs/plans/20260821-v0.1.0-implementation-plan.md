# dsh-hub v0.1.0 implementation plan

Language: English | [简体中文](20260821-v0.1.0-implementation-plan.zh.md)

This document records the public v0.1.0 MVP implementation baseline and forward
plan without private operational details.

## 1. Completed MVP slices

| Slice | Area | Public completion evidence |
| --- | --- | --- |
| M1A | Security and credential lifecycle | Unit/security tests for registry key, token, replacement grant, ACL, CSRF, Origin, and audit behavior |
| M1B | Bounded relay protocol | Protocol and tunnel tests for HTTP, WebSocket, cancel, credit, heartbeat, and backpressure |
| M1C | Real DSH compatibility baseline | Local real-DSH checks for core HTTP/WS seams |
| M2 | Deployment templates | Compose/Caddy/Authelia checks for local and existing-Caddy templates |
| M3A | Diagnostics | Owner-only diagnostics API and portal action |
| M3B | Operations baseline | Metrics, alert rule checks, recovery rehearsal, logging and redaction checks |
| M4 | Plugin-first integration | Plugin install/join/runtime/status/diagnostics/remote capability tests |

## 2. Verification commands

```bash
npm test
npm run deploy:m2:check
npm run deploy:m2:check:deep
npm run deploy:m2:existing-caddy:check
npm run deploy:m2:existing-caddy:check:deep
npm run deploy:m3:alerts:check
npm run deploy:m3:recovery:check
npm run deploy:m3:logging:check
```

Some deep deployment checks require Docker.

## 3. Public release rules

- Do not commit real `.env` files.
- Do not commit real Authelia user databases.
- Do not commit real secret files, SQLite databases, backups, logs, or local DSH
  credentials.
- Use `hub.example.com` and reserved IP addresses in public docs and tests.
- Keep private deployment runbooks in a private overlay repository.
- Treat successful template checks as template evidence, not production proof.

## 4. Post-MVP implementation order

The public roadmap is maintained in `docs/ROADMAP.md`.

Recommended order:

1. Session history lazy loading and large-history performance.
2. Production release hardening.
3. Multi-user roles and permissions.
4. Admin console.
5. DSH version compatibility matrix.
6. Hosted DSH container evaluation.
7. Hosted DSH pool auto-assignment, after permissions and admin operations are
   defined.

## 5. Review checklist

Before merging public changes:

1. Inspect changed files and run `git diff --check`.
2. Run tests proportional to risk.
3. Scan changed docs for real domains, IPs, local paths, credentials, and private
   project names.
4. Update README, protocol docs, roadmap, release notes, and operations docs
   when behavior changes.
5. Keep protocol changes synchronized with fixtures and tests.
