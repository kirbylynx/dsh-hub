# dsh-hub v0.1.0 requirements

Language: English | [简体中文](20260821-v0.1.0-requirements.zh.md)

This document describes the public v0.1.0 MVP requirements baseline without
private deployment evidence or local environment details.

## 1. Product goal

dsh-hub provides a remote access/control center for DeepSeek Harness (DSH)
instances that normally listen only on loopback. A user authenticates to the hub,
selects an authorized namespace and instance, and opens the original DSH Web UI
through a secure outbound tunnel.

## 2. Core terms

| Term | Meaning |
| --- | --- |
| namespace | Tenant or logical grouping owned by a user in v0.1.0 |
| registry key | Namespace-level registration key for new instances |
| instance | One registered DSH endpoint |
| instance token | Long-lived instance credential used by tunnel clients |
| replacement grant | Short-lived, one-time recovery credential approved by an owner |
| delivery | Instance-side mode: `plugin` or `agent` |

## 3. MVP requirements

### 3.1 Center and portal

- The center service must expose namespace, instance, registration, tunnel,
  health, metrics, and portal endpoints.
- Portal write operations must require authenticated user identity, exact Origin
  validation, CSRF, strict request schemas, and idempotency keys where secrets
  are issued.
- Portal read operations must enforce ACL checks and return minimized fields.
- The portal must not expose registry key digests, replacement grants, instance
  token digests, pepper key IDs, installation IDs, or internal database IDs.

### 3.2 Namespace and registry key

- v0.1.0 uses a single-owner namespace model.
- Each namespace has exactly one currently active registry key.
- The current registry key can register multiple new installations.
- Rotating a registry key invalidates the old key for future registration only.
- Rotating a registry key must not revoke, rotate, disconnect, or otherwise
  affect already issued instance tokens.

### 3.3 Instance registration and lifecycle

- New instances register with a namespace registry key.
- Previously bound installations must not silently re-register with a registry
  key; recovery requires a replacement grant.
- Instance tokens can be rotated by the instance.
- An instance can self-leave and clean local credentials after confirmed revoke.
- Owners can revoke instances; revoke terminates active tokens and tunnels.

### 3.4 Tunnel and relay

- The tunnel protocol must support HTTP, WebSocket, cancellation, flow control,
  heartbeat, health reporting, and bounded resource usage.
- The relay must strip center credentials and identity headers before forwarding
  to DSH.
- Responses must strip hop-by-hop headers and center-internal headers.
- Large or slow streams must be bounded by configured limits and backpressure.

### 3.5 DSH integration

- The recommended v0.1.0 path is plugin-first.
- The standalone client remains a fallback and diagnostic tool.
- DSH Web UI should be opened as a full-page instance subdomain.
- iframe embedding remains experimental.
- Remote directory selection should use a browser-oriented picker overlay where
  available, not the instance machine's native picker.
- Remote `openPath` should be disabled/gated until a safe replacement exists.

### 3.6 Deployment and operations

- Public examples must support:
  - local all-in-one Docker Compose;
  - backend services behind an existing system Caddy;
  - Authelia-based authentication;
  - example-only secret files;
  - metrics and alert rule checks;
  - local backup/restore rehearsal;
  - log retention and redaction checks.
- Real secrets, real hostnames, real IPs, and real operational notes must not be
  committed to the public repository.

## 4. Non-goals for v0.1.0

- Multi-user roles, shared namespaces, and member management.
- Admin console.
- Session history lazy loading.
- Hosted DSH container pool.
- Headless automation API.
- P2P or high availability.
- Strong hostile-tenant SaaS isolation.
- Remote `openPath` replacement UI.

## 5. Acceptance criteria

- `npm test` passes.
- Protocol fixtures match `docs/protocol.md`.
- Deployment-template checks pass for local and existing-Caddy examples.
- Public documentation contains only generic example domains and paths.
- Secret examples are clearly marked as insecure placeholders.
