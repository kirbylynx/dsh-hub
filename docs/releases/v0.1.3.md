# dsh-hub v0.1.3 closeout

Language: English | [简体中文](v0.1.3.zh.md)

v0.1.3 closes the first hosted DSH model/provider settings baseline. It keeps
the existing tunnel wire protocol unchanged and adds a narrow hosted-only
settings path inside the DSH Web dsh-hub plugin card.

## What changed

- Added non-secret `deploymentMode` metadata so instances can be shown as
  `remote`, `hosted`, or `unknown` in Portal and plugin status surfaces.
- Added service-side persistence for `deployment_mode` with a schema v2
  migration from the v1 database.
- Added hosted DSH composition support for `DSH_HUB_DEPLOYMENT_MODE=hosted`.
- Added same-origin plugin endpoints for hosted model settings:
  - `GET/HEAD/POST /plugins/dsh-hub-plugin/model-settings.json`
  - `POST /plugins/dsh-hub-plugin/model-settings/test.json`
- Added a narrow browser-card UI for hosted instances covering:
  - DeepSeek official provider settings;
  - OpenAI-compatible/custom Base URL providers;
  - `openai-completions` and `openai-responses` protocol choices;
  - provider model IDs and default model selection.
- API keys are written only to the hosted DSH local credential store. They are
  not stored in the Hub service database, Portal payloads, status payloads, or
  diagnostics.
- Read responses expose only credential status such as `configured` and
  `managed`; they do not return API key values or raw credential reference
  names.
- Blank API key input preserves existing credentials, including existing
  DeepSeek credential references.

## Security and compatibility

`deploymentMode` is optional metadata, not an authorization token. Hosted model
settings require local hosted eligibility checks, including explicit hosted
mode, a hosted marker, writable hosted workspace root, writable DSH settings and
credentials seams, and the expected model-provider namespaces.

Missing or invalid `deploymentMode` values are treated as absent. Register and
tunnel hello continue to accept old clients, and an invalid hello value does not
clear a previously recorded valid mode.

No tunnel frame changed in v0.1.3. The service, client, and plugin continue to
use protocol `proto: 1` and `minor: 1`.

## Verification

The closeout was verified with:

- `git diff --check main..HEAD`
- `npm run test:g13:hosted-model-settings`
- `npm run deploy:g11:hosted-dsh:check`
- `npm audit --omit=dev --audit-level=high`
- `npm test`

The final review also scanned for real domains, server IP addresses, local user
paths, and real-looking secret values. Public examples remain generic; real
deployment evidence belongs in operator-owned private overlays.

## Still out of scope

v0.1.3 does not add multi-user roles, Portal-side model administration, an admin
console, automatic hosted instance assignment, a full DSH settings bridge,
remote `openPath` replacement UI, a headless control API, P2P, or multi-center
routing.

## Operational note

Deployments running v0.1.2 should redeploy the Hub service and hosted DSH
container images so the service schema, Portal mode display, plugin browser
card, and hosted entrypoint all run the same v0.1.3 code.
