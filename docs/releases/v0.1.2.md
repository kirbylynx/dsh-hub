# dsh-hub v0.1.2 closeout

Language: English | [简体中文](v0.1.2.zh.md)

v0.1.2 closes the first bounded large-session history loading baseline. It keeps
the existing relay wire protocol unchanged and improves the remote DSH Web UI
path by limiting how much history is requested, normalized, buffered, and logged.

## What changed

- Added instance-side handling for DSH `session.history` and
  `subagent.history` HTTP API calls.
- Caps remote history requests to `maxMessages=20` by default.
- Normalizes DSH event-style history responses before they leave the instance:
  settled `assistant/chunk` records are removed while enough initial chunk
  context is preserved for rendered assistant messages.
- Adds separate raw and normalized history response limits. The default raw
  history response cap is 8 MiB; the normalized response target is 512 KiB with a
  1 MiB hard cap.
- Adds browser-side remote-origin-gated history autoload: remote sessions show
  the newest messages first, then load older history as the user scrolls upward.
- Adds history-specific error classification and retry guidance without logging
  DSH payload content, local paths, API keys, registry keys, replacement grants,
  or instance tokens.

## Configuration

The defaults are intentionally conservative and can be tuned by operators:

- `DSH_HUB_HISTORY_MAX_MESSAGES`
- `DSH_HUB_HISTORY_TARGET_BYTES`
- `DSH_HUB_HISTORY_HARD_BYTES`
- `DSH_HUB_HISTORY_MAX_RAW_BYTES`
- `DSH_HUB_HISTORY_NORMALIZER=off`
- `DSH_HUB_HISTORY_AUTOLOAD=off`

`DSH_HUB_HISTORY_MAX_RAW_BYTES` is also bounded by the existing relay HTTP body
limit so a history response cannot silently bypass the tunnel memory envelope.

## Verification

The closeout was verified with:

- `node --check packages/dsh-hub-client/src/relay.js`
- `node --test packages/dsh-hub-client/test/tunnel.test.js`
- `npm test`
- `npm run test:m4:feasibility`
- `npm run deploy:m2:check:deep`
- `npm run deploy:m2:existing-caddy:check:deep`
- `npm run deploy:g11:hosted-dsh:check`
- `npm audit --omit=dev --audit-level=high`

Manual remote dogfood also confirmed that a previously problematic large session
loads cleanly through the remote browser path. Detailed private deployment
evidence, domains, server addresses, and logs are intentionally not included in
the public repository.

## Still out of scope

v0.1.2 does not add multi-user roles, an admin console, hosted model/provider
configuration, a remote `openPath` replacement UI, a headless control API,
per-user DSH session isolation, automatic hosted instance assignment, P2P, or
multi-center routing.

## Protocol compatibility

No tunnel wire frame changed in v0.1.2. The service, client, and plugin continue
to use protocol `proto: 1` and `minor: 1`.
